## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/bart_zero_shot_classification_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 7-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/bart_zero_shot_classification_input_manifest.json` — the batch of texts, the label set, `multi_label`, the hypothesis template and the resulting hypotheses, the schema and ceilings, the verdict, and one recorded rejection finding (a duplicate label); `evaluation_report` (EVAL21) writes `outputs/bart_zero_shot_classification_evaluation_report.json`, whose one metric id, `accuracy`, is the repository's own helper (EVAL2) and whose verdict is `sample-sanity` on the three author-labelled sentences (a plumbing check, single pass, no dispersion) or `not-measurable` when no gold labels are supplied, with `needs` naming the labelled and calibration data a real evaluation requires (EVAL9).
- The notebook exercises `BARTZeroShotClassificationPipeline` carried verbatim in the notebook rather than reimplementing model loading or scoring; the pipeline pins the immutable upstream revision, stages the missing snapshot file through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses remote model code. No cell outside the carried module calls `transformers` or `huggingface_hub`, and no cell outside it computes a softmax.
- Score semantics (UNC1–UNC4): the score is an entailment-derived softmax — across labels when `multi_label=False`, per label over `[contradiction, entailment]` otherwise — a ranking signal that moves with the label wording, not a calibrated probability; the default decision rule is `argmax` (first entry); the pipeline ships no threshold and the caller owns any cut-off. The raw `entailment_logit`/`contradiction_logit` per label are printed and exported.
- §20.1 classification: the label set is caller-supplied at call time, so no fixed class vocabulary exists; the notebook states this, exports one row per (text, label) with the rank in `outputs/bart_zero_shot_classification_scores.csv`, and presents the author-expected-label check as a plumbing check and the `accuracy` as sample-sanity. The model card's smoke observations are quoted as one measurement, not expected values. Recorded `SHOULD` deviation: EVAL11 (no baseline — a majority-class baseline is meaningless over three items with three distinct labels).
- Ceilings `MAX_TEXT_CHARS`, `MAX_TEXT_TOKENS` (per premise+hypothesis pair; reject, never truncate), `MAX_LABELS`, `MAX_LABEL_CHARS`, `HYPOTHESIS_TEMPLATE`, `NUM_NLI_LABELS`, `ENTAILMENT_INDEX`, `CONTRADICTION_INDEX` are surfaced before the model runs (DAT22/DAT23).
- The default sample is synthetic text authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
